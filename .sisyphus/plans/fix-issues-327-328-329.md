## Task B — #328: `ON DUPLICATE KEY UPDATE NOTHING`

### B1. AST: convert struct → enum (mirror `ConflictAction` precedent)

File: `src/ast/mod.rs:1546-1550`

Current:
```rust
pub struct OnDuplicateKeyUpdate {
    pub assignments: Vec<UpdateAssignment>,
    pub where_clause: Option<Expr>,
}
```

New:
```rust
#[derive(Debug, Clone, PartialEq, serde::Serialize, serde::Deserialize)]
pub enum OnDuplicateKeyUpdate {
    Nothing,
    Update {
        assignments: Vec<UpdateAssignment>,
        where_clause: Option<Expr>,
    },
}
```

Rationale: `ConflictAction` (ast/mod.rs:1564-1568) already models the identical "do nothing vs update" dichotomy for ON CONFLICT; consistency wins. JSON shape changes but no tests/references depend on the old shape (verified: only dml.rs, tests.rs, formatter/mod.rs reference it; no visitor/analyzer, no roundtrip tests).

### B2. Parser: branch on NOTHING

File: `src/parser/dml.rs:163-181` (inside `parse_insert`)

After `self.expect_keyword(Keyword::UPDATE)?;` add:
```rust
if self.try_consume_keyword(Keyword::NOTHING) {
    Some(OnDuplicateKeyUpdate::Nothing)
} else {
    // existing assignment loop (lines 164-174) + WHERE clause (175-180)
    Some(OnDuplicateKeyUpdate::Update { assignments, where_clause })
}
```

Notes:
- `Keyword::NOTHING` already exists (token/keyword.rs:410, Unreserved category, line 1808) — no lexer change.
- Must also handle: is `ON DUPLICATE KEY UPDATE NOTHING` valid with a following `WHERE`? openGauss "do nothing" form takes no assignments → no WHERE allowed. If parser encounters `WHERE` after NOTHING, let the outer INSERT continue → it will error naturally on leftover tokens ("expected end of DML"). Acceptable; do NOT add a WHERE branch to Nothing.
- `try_consume_keyword` returns bool and advances — verify helper exists on Parser (used elsewhere in codebase, e.g. `try_consume_ident_str`; check exact name at implementation time: `try_consume_keyword` vs `match_keyword`+`advance`). Use whichever exists.
